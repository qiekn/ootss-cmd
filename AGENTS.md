### Style and native syntax

- Follow the existing four-space indentation and same-line opening braces. Use `snake_case` for procedures, variables and fields, `Title_Snake_Case` for types, and `UPPER_SNAKE_CASE` for ordinary constants; retain external API names and established project exceptions.
- Section comments use the following format, with `:` at column 80:

```jai
// ----------------------------------------------------------------------------: context
```

- Preserve the user's backslash-based alignment of the delay constant identifiers in the input code.
- Use `name :: value` for constants and named procedures, `name := value` for inferred variables, and `name: Type = value` when the type matters. Use explicit widths at binary-format, game-memory and foreign-API boundaries. Keep default initialization; use `= ---` only when every read is preceded by a proven write and skipping initialization has a concrete benefit.
- Write Jai syntax directly: `*value` takes an address, `pointer.*` dereferences, and `pointer.field` accesses a member. Use `cast(Type)` for conversions and `#char "x"` for character literals. Jai `print` uses `%` placeholders, not C's `%d` or `%s`.
- Prefer an explicit cast where the destination type or representation matters; use `xx` only when the target is unambiguous. Validate ranges before narrowing or changing signedness, and validate finite floats at external-input boundaries. A cast is not input validation.

### Procedures and control flow

- Prefer straightforward procedures and structs with explicit state, initialization and cleanup. Extract shared behavior when it removes real duplication; use polymorphism, macros or operator overloading only for a concrete need. Do not emulate class hierarchies, constructors, destructors or implicit member calls.
- Return failures explicitly using the surrounding code's `bool` or multiple-return-value convention, such as `(value, error)`. Check status before consuming results; keep assertions for programmer invariants and handle invalid user input, files and OS failures as normal errors.
- Use `if value == { case ...; ... case; ... }` for value dispatch. Cases do not fall through by default; `#through` is explicit, and `break` exits an enclosing loop rather than a case.
- Jai numeric ranges `a..b` include both ends. Prefer iterating arrays directly; for index loops handle empty arrays and avoid unsigned `count - 1` underflow. Use named iterators in nested loops, and `for *` when modifying array elements in place.
- Nested procedures and lambdas do not capture runtime locals. Pass required state explicitly, including callback user data.

### Ownership, cleanup and temporary storage

- Make ownership clear for returned strings, array views, pointers and resource handles: document borrowing, transfer and required cleanup when not obvious. Struct and dynamic-array assignments do not deep-copy owned data. Do not return pointers or views into expired stack storage or freed buffers.
- Pair owned allocations and resources with the matching release routine and allocator. Place `defer` near acquisition in the scope that owns the resource, guarding failed acquisition or ownership transfer when necessary. Jai `defer` runs at block exit in reverse order, including on each loop iteration; it is not limited to function exit.
- Release nested owned elements before freeing their container. Use the appropriate APIs, such as `array_free` for owned array storage and `free_buffers(*builder)` for a string builder; borrowed views must not free their backing storage. Verify the installed module's signature rather than guessing whether a pointer is required.
- Keep `temp`, `tprint` and temporary string/array results within their allocator lifetime. Copy data into persistent ownership before storing it in console history, queued commands, editor state, caches or later callbacks. A copy made with the temporary allocator still has temporary lifetime.
- Use scoped allocator/context changes and `auto_release_temp()` for bounded scratch work when appropriate. Reset temporary storage only at an established owner-controlled boundary after all borrowers are finished; a helper must not reset its caller's scratch storage. Set a dynamic array or builder's allocator before its first allocation.

### Arrays and strings

- Distinguish fixed arrays `[N] T`, views `[] T` and resizable arrays `[..] T`. Use views for borrowed sequences and `*[..] T` when a procedure changes the caller's resizable-array header, count or capacity. Element writes through a view still affect the backing storage.
- Reserve capacity for known batch sizes. Do not keep element pointers or views across operations that may reallocate, remove or reorder their backing array; reacquire them afterward. Choose removal operations deliberately when timeline, history or command order must be preserved.
- Jai strings are counted bytes, not guaranteed NUL-terminated C strings. Respect `.count`, distinguish UTF-8 byte offsets from character positions, and use the existing UTF-8/UTF-16 helpers at Windows boundaries. Use `to_c_string` only for APIs expecting a C string, with storage that remains valid for the entire call or retained use.
- Build repeated text with `String_Builder` and convert once instead of repeatedly concatenating with `sprint`. Track builder-buffer ownership separately from the resulting string, including which allocator owns the result. Copy borrowed substrings when they must outlive their source.

### Modules, foreign calls and metaprogramming

- Reuse the standard modules and existing project helpers before adding replacements. Use `#load` for project source and `#import` for modules; follow nearby `#scope_file` and module-alias conventions to keep implementation names local.
- Foreign declarations and callbacks must match the actual ABI: parameter widths, pointer types, return values, calling convention, layout and alignment. Reuse Windows bindings where available. A `#c_call` callback does not receive Jai's implicit context; establish a valid context for the calling thread before calling context-dependent Jai procedures, following the existing platform code.
- Keep reflection and raw-memory casts behind validated kind, size, offset and bounds checks. Distinguish local pointers from remote-process addresses; use the existing validated memory reader/writer for game data.
- Keep build logic in Jai and the existing `first.jai` workspace flow. Use `#run`, `#insert` and polymorphic specialization only when they simplify a real requirement; avoid unnecessary generated code and compile-time work. Compile-time code can perform real I/O, so keep those effects explicit and do not make ordinary builds execute runtime game actions.

### Scripts and verification

- Keep project utility scripts in `scripts/`. Write scripts and any regression checks in Jai instead of Python. Use `#!/usr/bin/env jai` and `#run` for scripts, disable executable output, and pass script arguments after Jai's standalone `-` separator.
- For script-only entry points, use `set_build_options_dc(.{do_output = false})` and read `get_build_options().compile_time_command_line`; invoke them as `jai scripts/name.jai - <arguments>`.
- For Jai code changes, compile through the existing build entry and run the relevant existing checks. Add focused Jai regression checks for substantive parsing, ownership, state or boundary bugs when needed; exercise empty, invalid and failure cases. Verify optimized builds when touching build options, ABI, layout or behavior that depends on optimization. Documentation-only edits need no application build.

## Input automation

- `send` sends literal letter keys, including R as the R key. `send_alt` maps U/D/L/R to W/S/A/D; C sends the C key directly.
- `play [name]` reads a saved solution from `data/solutions.json` and sends it through the standalone `send_alt` path. An omitted name, including `play -rabbit`, resolves the current small level from the active scene. Explicit names may fall back to `data/custom_inputs.json` when no saved level matches; matching levels take precedence. Names are case-insensitive. Support the same `-speed` option, speed aliases and presets before or after the name, with shared parsing, validation and interruption behavior. Do not reset the game, open the editor, read coordinates, or import answers. Unknown names, empty/invalid solutions, unavailable current levels and invalid options must not send keys. Tab combines names from both files, deduplicates them case-insensitively, and completes available options.
- `do [name]` is a case-insensitive alias for `play [name]`, including the default current level, options, validation, playback, interruption behavior and Tab completion.
- Both commands expand digits immediately after a letter as its total repeat count: `w3` means `www`. Whitespace-separated digits are literal character-selection keys: `www 3 www` sends `www3www`. Input boundaries also separate digit keys.
- Support parenthesized repeats in the shared send parser: `send (ad)3` sends `adadad`, including nested groups and letter repeats inside groups. A count must immediately follow `)`, so `(ad) 3` sends `ad3`. Apply the same syntax to `send_alt` and Jai APIs; reject unbalanced/empty groups, zero repeats, and expansions beyond 65536 keys before injecting any input.
- `send`, `send_alt`, `play` and `do` support `-speed <N>` before or after the script (0 < N <= 4): during playback the game's base multiplier is temporarily set to `N × its current value`, clamped to 16, and restored on completion, cancellation or failure — the same mechanism as the editor's playback presets.
- Default key hold is 50 ms, leaving 200 ms of released time in the normal 250 ms cycle. For command and editor cycles use a hold of `min(50, max(1, delay / 2))` in integer milliseconds; the remainder is released time. For example 75 ms uses 37 ms + 38 ms, and 175 ms uses 50 ms + 125 ms. Keep explicit Jai API hold/interval arguments supported.
- `send` and `send_alt` (and their `play`/`do` wrappers) use the standard 250 ms game-time cycle; key cycles and waits follow the game speed, including a temporary `-speed` override. Speed presets are aliases of `-speed`, read from `config.rc`: `-fast` = `speed_fast` (default 2), `-superfast`/`-rabbit` = `speed_superfast` (default 4), `-slow` = `speed_slow` (default 0.5), `-superslow`/`-turtle` = `speed_superslow` (default 0.25); each value must satisfy 0 < value <= 4. Select at most one speed option; do not hold the game's fast/slow keys.
- `-rabbit` aliases `-superfast`, and `-turtle` aliases `-superslow`, for `send`, `send_alt`, `play` and `do`. Aliases are case-insensitive and share the exclusive speed selection.
- During independent `send` / `send_alt` playback, physical keyboard presses or mouse clicks/wheel input in the game interrupt the remaining sequence. Ignore injected events, allow the player's input through, and release all injected keys on completion, cancellation, focus loss, or failure. Keep these hooks separate from the solution editor's recording and playback; the temporary speed override uses the editor's base-multiplier mechanism but owns its own session.
- `undo` and `z` send Z to undo, once when no count is given. `undo 100`, `z 100`, and `z100` send 100 Z presses. Undo defaults to a 10 ms per-key cycle; `-fast` changes that default to 1 ms. Support `-delay <ms>` / `-delay <ms>ms` before or after the count; an explicit delay takes precedence over `-fast`. Counts must be positive and respect the existing send key limit.
- `reset` and `r` are case-insensitive aliases that send one literal R key. When the solution editor is open, an accepted reset key returns its playhead to zero while preserving the solution.
